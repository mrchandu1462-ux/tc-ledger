Trust & Boundaries

The Challenge: Transient Log Retention

Core Trust Boundary

Verification is conditional on trusted inputs. TC-Ledger verifies a retained export against a root you already hold. The cryptographic artifact does not establish the provenance of that root, authenticate envelope metadata, or provide trusted timestamping by itself.

Technocore Chat Streams

Technocore servers retain and emit raw JSONL exports of room conversations containing Ed25519-signed messages from decentralized identifiers (did:key:z6Mk...).

However, retained server history can become unavailable through storage retention and log eviction policies. When messages are evicted, counterparties and external auditors lose the ability to prove historical events unless export files and cryptographic anchors were preserved.

TC-Ledger allows preserved exports and evidence to be independently verified offline. You hold the proof. Keeping it is your responsibility.

Explicit Trust Boundaries

TC-Ledger is engineered with strict cryptographic conservatism. It operates exclusively on retained artifacts:

  • No History Recovery: TC-Ledger does not recover deleted history or reconstruct evicted records.
  • No Full Lifetime Claims: It does not prove complete room history prior to an export.
  • Retention Limitation: Eviction can destroy the retained bytes needed to independently verify earlier records. C7 therefore fails when the newer export is no longer an exact prefix of the earlier export.
Architecture

How It Works

A deterministic 8-stage cryptographic pipeline from signed wire records to offline verifier.

JCS vs. Raw-Byte Commitments: JCS provides deterministic semantic evidence identity; the Merkle commitment covers the exact retained export bytes. They are independent commitments and are not interchangeable. Re-serializing a semantically identical export can change its byte commitment.

Signed Technocore Activity

Author signs UTF-8 wire payload room|nonce|text with Ed25519 private key (did:key:z...).

↓
02

Ed25519 Signature Verification

Strict canonical Base64URL decoding (exactly 86 chars, zero unused bits) validates signature fail-closed.

↓
03

Deterministic Evidence Commitment

RFC 8785 JSON Canonicalization Scheme (JCS) produces semantic record ID: tc-ledger:v1:<sha256>.

↓
04

Exact Export-Byte Commitment

Commits to the exact physical line bytes in source order without re-serialization, preserving exact LF delimiters.

↓
05

Merkle Root

RFC 6962 tree hash with domain separation: leaf 0x00 || raw_bytes and node 0x01 || left || right.

↓
06

Inclusion Proof

Compact audit path allowing any individual physical line to be proven against a known Merkle root.

↓
07

Append-Only Consistency Proof

RFC 6962 §2.1.2 consistency proof proves that an earlier export generation is an exact prefix of a later export.

↓
08

Offline Independent Verification

Verifier holds only the single target record, the proof artifact, and expected root. Zero network calls.

C7 Protocol Layer

Cross-Generation Consistency: Append-Only vs. Eviction

C7 proves consistency between two roots when the newer tree contains the earlier tree as an exact prefix. It does not provide an external witness or prevent divergent histories by itself.

Valid Extension APPEND-ONLY ✓
Generation 1 (size 4):
A B C D
↓ Append new records
Generation 2 (size 6):
A B C D E F

Proof Verifies: [A B C D] → [A B C D E F]

Generation 1 forms the exact unaltered prefix of Generation 2. The RFC 6962 consistency proof verifies cryptographically without needing the full Generation 1 export file.

Server Retention Eviction NOT A PREFIX ✗
Generation 1 (size 4):
A B C D
⚠ Record A evicted by server storage policy
Generation 2 (size 5):
B C D E F

Proof FAILS: [A B C D] → [B C D E F]

Eviction can destroy the retained bytes needed to independently verify earlier records. C7 therefore fails when the newer export is no longer an exact prefix of the earlier export. Failing closed is mathematically correct; TC-Ledger refuses to assert false continuity or invent deleted history.

Specifications

Cryptographic Guarantees & Non-Guarantees

What TC-Ledger Proves

  • Ed25519 Signature Validity: Verifies that a record was signed by the private key corresponding to its declared did:key:z6Mk... identifier over canonical room|nonce|text.
  • Deterministic Evidence Identity: Normalizes valid payloads via RFC 8785 (JCS) to produce a unique evidence ID (tc-ledger:v1:<sha256>).
  • Exact Export-Byte Commitment: Binds physical lines in source order without re-serialization, preserving exact LF/CRLF delimiters and blanks.
  • Merkle Inclusion: Generates compact audit paths allowing any single export line to be proven against a known Merkle root. Preserved export lines are tamper-evident relative to a previously recorded root.
  • Append-Only Consistency: Cryptographically verifies that an export tree is an exact prefix extension of an earlier committed export tree.
  • Offline Verification: Verifies inclusion and consistency proofs independently with zero network calls or full export downloads.

What TC-Ledger Does NOT Prove

  • Entire Room Lifetime History: It verifies retained export bytes; it does not attest to messages pruned by room retention policies before export.
  • Factual Truth of Messages: It proves that an identity signed a specific statement; it does not prove the factual truth of the message contents.
  • Real-World Identity Attribution: It verifies signatures against public keys in did:key; it does not establish real-world identity or solve private key compromise.
  • Continuous Data Availability: It commits to and proves inclusion within export files, but does not provide distributed consensus or decentralized storage.
  • Unanchored Envelope Metadata: Envelope metadata (room, generations, tree sizes) are self-attested unless verified against caller-provided trust anchors.
